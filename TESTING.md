# Testing

## Automated (any OS)

```
dotnet test                                   # 50 tests, about 5 seconds
PARADIS_LARGE_TESTS=1 dotnet test --filter "FullyQualifiedName~LargeImageTests" --logger "console;verbosity=detailed"
```

All tests run the real engine against the real libvips on images generated by the tests. Last
run: 55 of 55 passed (Ubuntu 24.04, .NET 10.0.113, libvips 8.18.7, 4 cores, 16 GB).

What they cover:

- **Originals are safe.** The original's bytes and modified time are unchanged after processing;
  existing output files are never overwritten (`Image.png`, `Image (1).png` exist → `Image (2).png`);
  failed and cancelled images leave no `.partial` files and nothing in the output folder.
- **Resize.** Width only, height only, fit-inside-box, percentage, proportions off, don't-enlarge
  (small images copied byte for byte), EXIF orientation 6 (output upright, orientation reset to 1),
  transparency kept, 16-bit → 8-bit, CMYK JPEG → RGB, manual PNG/JPEG/WebP output.
- **Optimize.** Wasteful PNG → much smaller PNG with identical pixels; opaque alpha dropped with
  identical colour; an already-tight PNG and a quality-70 JPEG are copied unchanged ("Already
  efficient"); a quality-100 JPEG gets smaller; lossless WebP stays lossless and pixel-identical;
  lossy WebP keeps transparency.
- **Conversion.** Photo-like PNG → JPEG; screenshot-like PNG stays PNG; a PNG with any transparent
  pixel stays PNG with alpha; manual JPEG on a transparent PNG is skipped, never flattened.
- **Failures.** Truncated PNG and a JPEG with scrambled data ("Damaged or incomplete"), a text file
  named `.png` and a JPEG with an overwritten start ("Couldn't read image"), a BMP named `.jpg`
  ("Not a supported image"), a missing file, an image too wide for WebP; a bad image in the
  middle of a batch doesn't stop it; cancel keeps finished files and counts the rest.
- **GIFs with the wrong name.** An animated GIF named `.jpg` gives a PNG of its first frame only
  ("Done (GIF → PNG)"), original untouched; same size still saves a copy rather than copying the GIF;
  Save as JPEG/WebP respected (WebP lossless and exact); a transparent GIF stays PNG with
  transparency even with conversion allowed, and Save as JPEG skips it; a damaged GIF fails cleanly;
  the batch counts recovered GIFs and leaves them out of the space saved; real `.gif` files are not
  picked up.
- **Scanning.** Subfolders off by default; `Resized`/`Optimized` folders and the custom output folder
  are never scanned; partial files ignored; duplicates not added twice; a folder dropped directly is
  scanned even if it is called `Resized`.
- **Output layout.** Default folder next to each original (two source folders → two output folders);
  custom folder with subfolder structure; same names from different folders numbered.
- **Large images** (348 MB, 12000 × 10000 PNG): header in 1 ms; resize to 4096 wide in 10 s at
  275 MB peak; lossless optimize in 32 s at 135 MB; optimize + conversion to an 18 MB JPEG in 35 s
  at 175–304 MB; a batch of two huge images plus a truncated one finishes with 2 done and 1 failed at
  336 MB peak. A full decode of this image alone would be 360 MB.

## Not yet tested: the window on real Windows

The app was built and published from Linux. It starts under Wine (the log is written as
`ParadisResize-YYYYMMDD.log` and libvips loads from the DLL next to the exe), but WPF's text
rendering doesn't work under Wine, so the window itself has not been seen yet. Checklist for a
first run on Windows 10/11:

1. Unzip, run `ParadisResize.exe`; the dark window shows the drop area.
2. Drop a single image, several images, and a folder; with and without Include subfolders.
3. Add Files / Add Folder dialogs; Remove and Clear List; Delete key.
4. Resize: width only, height only, both, percentage; the Example line updates; invalid input
   (0, 70000) disables the button with a message.
5. Optimize, with and without format conversion; Save as JPEG on a PNG with transparency is skipped.
6. Choose Folder… and Use default; a folder you can't write to (e.g. `C:\Windows`) is refused.
7. A large PNG (100+ MB): the window stays responsive, the row shows "Working… N%", Cancel stops it
   and leaves no `.partial` file.
8. The summary: Open Output Folder with one folder; no button when copies went to several folders.
9. About, Log folder, More from Paradis EZ Utilities.
10. Close during a batch asks first; Windows display scaling at 150%.
11. An animated GIF renamed `.jpg`: the list shows GIF and "Ready (GIF, still image only)", the
    tooltip mentions the frames; after processing "Done (GIF → PNG)", the copy is a still PNG of the
    first frame, and the summary says a still was recovered.
